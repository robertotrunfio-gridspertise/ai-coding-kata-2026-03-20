The design pattern I would implement here is a small Policy-Based Design with an explicit Pricing Pipeline.

It is the best fit for this module because it improves extensibility without turning the code into a framework.

**Proposed Pattern**
Use three layers:

1. Pricing pipeline
   A single orchestrator that preserves the current execution order:
   - normalize input
   - resolve customer policy
   - compute base discount
   - apply promotion rules
   - cap discount
   - compute discounted subtotal
   - compute shipping
   - compute tax
   - compute total
   - clamp to zero

2. Customer policy
   Represent each customer type as a policy object or enum-backed behavior provider.
   This owns customer-specific behavior such as:
   - base discount
   - Black Friday discount behavior
   - free shipping threshold
   - shipping surcharge exception
   - tax exception if any

3. Promotion rules
   Represent coupon and event rules as small rule objects applied in a fixed sequence.
   These rules can affect:
   - discount
   - shipping
   - tax

This is effectively a hybrid of:
- Strategy for customer behavior
- Rule Object for promotions
- Template Method style orchestration in the calculator

**Why This Pattern Fits**
The current code in rust-kata/src/lib.rs has one main problem: all rule dimensions are mixed together in one flow.

Those dimensions are actually separate:
- customer type
- coupon
- country
- Black Friday
- final pricing order

The right move is not a big rewrite. It is to separate those axes while keeping the pipeline explicit.

That gives you:
- preserved behavior
- explicit rule order
- easy addition of a new customer type
- easy addition of a new promotion
- stable public API

**Concrete Shape**
I would evolve the current refactor into this structure.

1. Keep the public API unchanged
   - `Order`
   - `calculate_total_cents(&Order) -> i32`

2. Add an internal pricing context
   Example responsibilities:
   - normalized order data
   - accumulated discount percent
   - discounted subtotal
   - shipping cents
   - tax percent
   - final total inputs

3. Add a customer policy abstraction
   Small interface, for example:
   - `base_discount_percent`
   - `black_friday_discount_percent`
   - `free_shipping_threshold`
   - `employee_shipping_surcharge`
   - `tax_override_percent`

   In Rust, I would prefer one of these:
   - enum + methods
   - small trait with concrete zero-sized policy structs

   For this kata, enum + methods is probably simpler and easier to explain.

4. Add promotion rule abstractions
   Small rule units such as:
   - `Save10Rule`
   - `VipOnlyRule`
   - `BulkRule`
   - `FreeShipRule`
   - `TaxFreeRule`
   - `BlackFridayShippingRule`

   Each rule should do one thing only.

5. Keep rule ordering explicit in the calculator
   This part matters a lot.
   Do not make promotions unordered or data-driven in the first step.

   The current behavior depends on sequence, especially for:
   - free shipping followed by employee surcharge
   - US Black Friday surcharge before free shipping reset
   - Italy VIP tax override
   - `TAXFREE` outside Italy only

So the calculator should still read like a clear script, but each step should delegate to a small component.

**Minimal Architecture**
A simple version would look like this conceptually:

- `NormalizedOrder`
- `PricingContext`
- `CustomerKind`
- `CouponKind`
- `CustomerPolicy` behavior on `CustomerKind`
- `PromotionRule` functions or structs
- `PricingCalculator` orchestrator

That keeps the design understandable and still small.

**What I Would Implement First**
I would not jump directly to trait-heavy polymorphism everywhere.

I would do this in order:

1. Parse strings into internal enums with fallback
   - `CustomerKind`
   - `CountryKind`
   - `CouponKind`

   Important:
   preserve unknown fallback behavior.

2. Move customer behavior behind enum methods
   This is the first real extensibility gain.

3. Extract promotion rules into focused functions or tiny structs
   Only after customer behavior is separated.

4. Introduce `PricingContext`
   Only if the shipping/tax rule application becomes clearer with it.

This keeps the refactor incremental and safe.

**Best Pattern Name To Use**
If you need to name the pattern in the solution, I would call it:

Policy-Based Pricing Pipeline

That is more accurate than forcing a textbook label like Strategy everywhere.

If you want a more formal label, say:

Strategy + Rule Object with explicit orchestration

**Why Not Other Patterns**
I would avoid these for now:

1. Full Chain of Responsibility
   Too opaque for a pricing flow where order and state transitions must stay obvious.

2. Generic rules engine
   Overkill for this kata and harder to explain.

3. Trait-per-customer plus trait-per-coupon everywhere
   Works, but likely too abstract for the current size.

4. Table-only configuration
   Not enough, because some rules are conditional and ordering-sensitive.

**How This Helps New Features**
If you later add:
- a new customer type like `partner`
- a new promotion like `PARTNER5`

you should only need to:
1. add one customer policy
2. add one promotion rule
3. register them in the pipeline

instead of editing multiple unrelated branches in one large function.

**Tradeoffs**
Pros:
- preserves current behavior
- keeps tests unchanged
- improves extensibility
- keeps rule order visible
- still simple enough for a kata
- easier to explain in `solution.md`

Cons:
- more types than the current single-file approach
- some boilerplate appears
- if overdone, can become abstraction-heavy
- requires discipline to keep the pipeline explicit

**Recommendation**
Implement a Policy-Based Pricing Pipeline, starting with:
1. internal enums for customer, country, and coupon
2. customer behavior as enum methods
3. promotions as focused rule units
4. one orchestrator that preserves the current order exactly

That is the smallest pattern-based design that genuinely improves extensibility without breaking the constraints.
