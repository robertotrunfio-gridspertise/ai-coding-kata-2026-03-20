**Current Observable Behavior**
The public behavior is defined by `calculate_total_cents(order: &Order) -> i32` in lib.rs.

At a high level, it does this in order:

1. Reads and normalizes input strings with `safe()`
   - `customer_type`, `country`, and `coupon_code` are trimmed before any rule evaluation in lib.rs.
2. Computes a percentage discount
   - customer-type discount first
   - coupon discount second
   - Black Friday bonus third
   - capped at 40% in lib.rs.
3. Applies that discount to subtotal
   - integer arithmetic is used, so fractional cents are truncated in lib.rs.
4. Computes shipping
   - base country shipping first
   - then Black Friday US surcharge
   - then free-shipping rules
   - then employee surcharge in lib.rs.
5. Computes tax
   - based on country
   - with VIP-in-IT override
   - with `TAXFREE` override outside IT in lib.rs.
6. Returns `discounted_subtotal + shipping + tax`
   - but clamps negative totals to `0` in lib.rs.

**Pricing Rules**
Customer discount rules are in lib.rs:

- `vip` gets 15%
- `premium` gets:
  - 10% if subtotal is at least `10000`
  - 5% otherwise
- `employee` gets 30%
- `regular` and `new` get 0%
- any unknown customer type also gets 0%

Coupon discount rules are in lib.rs:

- `SAVE10` adds 10% only if subtotal is at least `5000`
- `VIPONLY` adds 5% only if customer type is `vip`
- `BULK` adds 7% only if subtotal is at least `20000`

Important detail:
- these coupon rules are mutually exclusive because they are written as `if / else if / else if` in lib.rs
- only one of those coupon-discount branches can ever apply

Black Friday discount rule is in lib.rs:

- adds 5%
- except for `employee`, who does not get the Black Friday discount bonus

Discount cap is in lib.rs:

- if total discount goes above 40%, it is reduced to 40%

**Shipping Rules**
Shipping rules start in lib.rs.

Base shipping by country:
- `IT` -> 700
- `DE` -> 900
- `US` -> 1500
- any other country -> 2500

Adjustments:
- if Black Friday and country is `US`, add 300 in lib.rs
- if coupon is `FREESHIP` and discounted subtotal is at least `8000`, shipping becomes 0 in lib.rs
- if customer is `vip` and discounted subtotal is at least `15000`, shipping becomes 0 in lib.rs
- if customer is `premium` and discounted subtotal is at least `20000`, shipping becomes 0 in lib.rs
- if customer is `employee` and country is not `IT`, add 500 in lib.rs

Important detail:
- shipping rules are not mutually exclusive
- later rules can override earlier ones, or re-add charges after shipping was set to zero

**Tax Rules**

Tax is computed on the discounted subtotal, not on subtotal plus shipping, in lib.rs.

**Observable Pattern**
There is a clear execution pattern:

1. normalize strings
2. accumulate percentage discount
3. cap discount
4. compute discounted subtotal
5. derive shipping from country and mutate it with promotions/surcharges

There is also a structural pattern:
- customer type drives both discount and shipping and sometimes tax

- country drives both shipping and tax
- Black Friday affects both discount and shipping

So the module is effectively a single rule engine encoded as sequential condition chains inside one function.

**Design Flaws**
Without refactoring, the main design issues are:

1. Too many responsibilities in one function
   - discounting, shipping, tax, normalization, and final validation all live in lib.rs.

2. Rules are encoded as hard-coded string comparisons
   - customer types, countries, and coupons are all magic strings.

3. Hidden rule ordering
   - behavior depends heavily on the order of conditions
   - especially in shipping and tax overrides.

4. Mixed rule styles
   - some rules add percentages
   - some overwrite shipping
   - some re-add shipping later
   - some overwrite tax
   - this makes mental execution expensive.

5. Implicit coupling across concerns
   - shipping thresholds depend on discounted subtotal
   - tax depends on discounted subtotal
   - coupon meaning changes by section.

6. No explicit domain model for business concepts
   - there is no typed representation of customer tier, coupon kind, country, or promotion.

7. Silent fallback behavior
   - unknown customer types and countries are accepted without validation and produce default behavior.

8. Low extensibility
   - adding a new customer type or coupon requires editing multiple conditional areas in the same function.

9. Dead or near-dead defensive branch

10. No local documentation of intent

11. No test evidence on this branch
